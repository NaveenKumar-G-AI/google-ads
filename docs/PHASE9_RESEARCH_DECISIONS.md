# Phase 9 Research Decisions

## 1. Identity and tenant authorization are separate

Supabase Auth access tokens are used only to authenticate a user. A tenant identifier, role,
or advertiser authorization supplied by the browser is not trusted. Membership is resolved
from the application database on every tenant-scoped request.

## 2. Asymmetric JWT verification only for production

Supabase currently recommends asymmetric signing keys and exposes public keys through JWKS.
Phase 9 supports ES256 and RS256. Shared-secret HS256 is deliberately excluded from this API
boundary so the web API does not need the project's JWT signing secret.

Validation includes signature, issuer, audience, expiration, subject, and the `authenticated`
role claim.

## 3. No service-role token as an end-user identity

A privileged Supabase service-role/secret token is not a person. Accepting it as a user would
collapse authentication and backend privilege boundaries. The verifier rejects it.

## 4. Least privilege product roles

Viewer and analyst roles cannot authorize Google Ads mutations. Business Truth changes and
proposal decisions can alter future financial conclusions, therefore they are admin/owner
operations in V1.

## 5. Durable job boundary instead of request-bound Google work

Google syncs, analysis and mutations are queued. The HTTP process must not be responsible for
finishing a potentially long external action after returning a response or surviving browser
disconnects/redeploys.

## 6. Exact-endpoint idempotency

Job-producing endpoints require an idempotency key. Idempotency identity includes the exact
endpoint and canonical request digest. Reusing a key with different input is a conflict rather
than guessing which operation the user intended.

## 7. Server-owned Business Truth provenance

The client may submit business facts, but it cannot choose the authoritative `created_by` or
`created_at`. Those are derived at the backend boundary. This prevents backdating or assigning
another user as the submitter.

## 8. Linear Business Truth versions

For each `business_id`, truth versions form one chain. Phase 9 indexes business/version fields
inside PostgreSQL and enforces one version number per tenant/business. API code requires the
next version to supersede the current version.

## 9. Apply and rollback are different authorization problems

Applying requires an approved immutable proposal. Rollback requires proof of an actual
`applied` mutation event and its exact Google resource name. Keyword text alone is not a
sufficient rollback target.

## 10. Web membership policy is read-only

The normal web RLS policy lets an authenticated user read their own memberships. It does not
permit web-path membership inserts/updates. Membership administration will require a separate
privileged control plane rather than an ordinary tenant endpoint.

## 11. No direct browser database model

The intended topology is browser → backend API → PostgreSQL. The backend database credential
must never be exposed to the browser. Direct Data API/browser access would require a different
JWT-native RLS design and a separate security review.

## 12. Business Truth is advertiser-account scoped

A tenant can contain multiple Google Ads advertiser accounts. Business rules from one account
must not silently authorize exclusions in another. Every Phase-9-created Business Truth snapshot
is bound to an internal Google Ads account ID, and analysis requires the truth snapshot to belong
to the same account as the completed sync.

## 13. HTTP idempotency is not enough for mutations

A caller could choose two different idempotency keys for the same approved proposal before the
first worker reaches Google. Apply/rollback jobs therefore also use a unique domain operation key
(`proposal:<id>:apply` / `proposal:<id>:rollback`). This closes a race that ordinary HTTP retry
idempotency does not address.

## 14. Immediate immutable writes are also idempotent

Business Truth creation requires an Idempotency-Key. Its authoritative timestamp is generated by
the server, so request replay must return the original snapshot rather than creating a second
timestamped version. Idempotency records are append-only in V1.
